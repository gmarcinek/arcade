## Blockers

### 1. `updateBallPositionFromFrame` position/quaternion overwritten by `updateCarVisuals`

**File**: `src/main.js` — PROCEDURAL_PLAYER branch in `tick()`

**What breaks**: The call order is:

```js
updateBallPositionFromFrame(carGroup, frame); // sets position + quaternion from procedural frame
updateCarVisuals(dt, ballObjects, renderer, scene); // overwrites both immediately after
```

Inside `updateCarVisuals` (ball.js ~line 160) the very first substantive lines are:

```js
const basis = getBasis(state.carTheta); // carTheta = 0 — never updated in procedural path
const r = TUNNEL_R - CAR_OFF - state.radialOffset;
carGroup.position.set(
  basis.surfaceOut.x * (r - 0.65),
  basis.surfaceOut.y * (r - 0.65),
  state.carZ, // carZ = 0 — never updated in procedural path
);
// …
const matrix = new THREE.Matrix4().makeBasis(
  basis.right,
  basis.up,
  basis.forward,
);
carGroup.quaternion.setFromRotationMatrix(matrix); // also overwrites quaternion
```

Result: the ball is always rendered at theta=0, z=0 on the legacy tube wall — it never moves to the procedural surface position. M3-4's requirement ("ball visible at correct tube-wall position when `PROCEDURAL_PLAYER = true`") is not met.

**Fix**: move `updateBallPositionFromFrame` to _after_ `updateCarVisuals`:

```js
updateCarVisuals(dt, ballObjects, renderer, scene); // legacy position/quat set here
updateBallPositionFromFrame(carGroup, frame); // now overrides with procedural values
```

## Notes

- **curves.js** — theoretical NaN path: if `initialNormal` is exactly parallel to `tangents[0]`, the Gram-Schmidt projection yields a zero vector; `normals[0]` becomes `(0,0,0)`, propagating NaN frames. In practice the chunk generator constructs normals that are always roughly perpendicular to the next tangent, so this will not trigger on the main path. Worth a guard (`if (n0.lengthSq() < 0.001) fall back to cross-product`) in a follow-up.

- **advanceToNextSegment null case** — when the chunk pipeline hasn't generated the next segment yet (single-frame stall), `playerSurface.js` clamps `state.s = segLen - 0.1` and the advance is retried on the next frame after `chunkManager.update()` has filled the window. This is a one-frame hitch, not a loop.

- **Flythrough camera** (`getSafeTrackUAt`, `updateFlythroughCamera`) still hardcodes `demoTrack.surfaces[0]`. Once old segments are evicted from the sliding window that reference will point to the wrong (or removed) segment. Non-blocking for the game path, but the flythrough preview will break after the player advances past the first chunk.

- **`PROCEDURAL_PLAYER` is hard-coded `true`** — the legacy path cannot be exercised via config; a comment or a `false` path test would confirm regression-safety.

## Summary

The build is clean and all module wiring (imports, exports, state initialisation, chunk pipeline, camera null-guard) is correct. One functional blocker: `updateCarVisuals` runs after `updateBallPositionFromFrame` and unconditionally overwrites `carGroup.position` and `carGroup.quaternion` with legacy theta/carZ values, so the ball never appears on the procedural surface. Moving the `updateBallPositionFromFrame` call to after `updateCarVisuals` is the single required fix.
